# MPLADS ML Data Package

Onboarding document for an ML engineer taking over this dataset. Read this once, top to
bottom, and you should not need to ask the previous developer anything.

Every number in this file is measured from the current extract and regenerated by
`python -m mplads_audit.export_package`. If a number here disagrees with something in
`docs/`, this package and `metadata/data_quality_report.md` are correct — `docs/` holds
dated narrative reports, some of which predate corrections (see §9 and §20).

---

## 1. What this dataset represents

Every work funded under **MPLADS** (Members of Parliament Local Area Development Scheme)
that appears in the public eSAKSHI reporting tables: what was recommended, by which MP,
in which state and constituency, implemented by which district authority, for how much,
and whether it reached sanction and completion.

- **210,987 works** (canonical, one row each, unique `work_ref`)
- **476,781 lifecycle stage records** behind those works
- **36 states/UTs · 545 constituencies · 778 implementing agencies**
- **85,525 works with a full recommendation→completion lifecycle**
- **125,220 works still open** at the extract date (2026-05-26)
- Recommendation dates span **2019-05-23 → 2026-05-26**

This is **real government data**. It is not simulated, not sampled, and not anonymised —
it is already public.

## 2. Problem being solved

MPLADS monitoring is manual and reactive: no official can inspect 210,987 works. The
system finds works that are **unusual relative to genuinely comparable works**, estimates
which are at risk of not completing and how much money that involves, detects when an
implementing agency's behaviour changes, and ranks where limited audit capacity should go.

**Critical framing, enforced throughout the package:**

> **ANOMALY / INVESTIGATION LEAD ≠ FRAUD FINDING.**

There are **no fraud labels** in any public MPLADS source. Nothing here is a supervised
fraud model, no output is a fraud probability, and no metric in this package is a
real-world fraud rate. `outputs/triage_results.csv` carries a `not_a_fraud_finding`
column on every row so the caveat cannot be stripped by a downstream consumer.

## 5. Canonical work-level dataset

`processed/mplads_work_level.csv` — **DERIVED FROM REAL.** 210,987 rows × 31 columns,
one row per work, keyed by `work_ref`.

### How it is built from the raw stage records

Raw files carry **one row per work-stage**, not per work. `mplads_audit/load_real.py:build()`
performs, in this exact order:

1. **Concatenate** the three eSAKSHI stage files.
2. **Drop rows with a null join key** — `(WORK_RECOMMENDATION_DTL_ID, mp_id)`.
   480,768 → 476,781 rows (**3,987 dropped, 0.83%**). Those rows cannot be attached to any
   work; they remain in `raw/`.
3. **Split by stage** (`tile_label`):
   - `Works Recommended` → sorted by `RECOMMENDATION_DATE`, `drop_duplicates(key, keep="first")`,
     supplying descriptive and amount fields.
   - `Works Sanctioned` → deduplicated key list only, becoming the boolean `is_sanctioned`.
     **The source carries no sanction date**, so sanction timing is unknowable.
   - `Works Completed` → `drop_duplicates(key, keep="first")`, supplying `WORK_ID`,
     `ACTUAL_AMOUNT`, `ACTUAL_END_DATE`, `AVERAGE_RATING`.
4. **Outer-join** the three on the key, so a work missing any stage is still represented.
5. **Rename** to unambiguous names (`STATE_NAME` → `state_name`, `IDA_NAME` →
   `implementing_agency`, …).
6. **Amounts**: `to_numeric(errors="coerce")`; drop rows where `recommended_amount <= 0`
   (**6 rows**). Nulls are kept (0.329%).
7. **Dates**: `to_datetime(errors="coerce")`. 0.329% of recommendation dates fail to parse.
8. **Set the as-of anchor** = maximum **recommendation** date = **2026-05-26**.
9. **Derive** `is_completed`, `is_backdated`, `is_future_dated`, `delay_days` (nulled when
   either date flag is set), `duration_days`, `event_observed`, `financial_year`,
   `scale_bucket`, `work_status`.
10. **Build `work_ref`** = `"MP" + mp_id + "-W" + rec_dtl_id`.

Duplicate handling is `keep="first"` after sorting by recommendation date — the earliest
recommendation row wins. **No aggregation and no imputation is performed anywhere.**

### Why `work_ref` and not `WORK_ID`

`WORK_ID` is populated **only on Completed rows** (0% on Recommended and Sanctioned), so
it is null for all 125,220 open works. It is preserved in the work-level file for
traceability but identifies nothing. `work_ref` is unique across all 210,987 rows
(**0 duplicates**).

## 9. Known data-quality issues

Measured, not assumed. Full detail in `metadata/data_quality_report.md` §8.

1. **`WORK_ID` unusable as a key** — 0% populated on Recommended/Sanctioned rows.
2. **6 non-positive amounts** dropped at load; still present in `raw/` and the events file.
3. **1,191 back-dated works** (completion before recommendation). Flagged `is_backdated`,
   `delay_days` nulled so they cannot corrupt the survival fit, and they raise the
   conformance signal as a data-quality lead. *(Earlier project docs say 1,194; this extract
   measures 1,191 after the 6 non-positive rows are dropped.)*
4. **9 out-of-window completion dates** (typed 2034, 2044, …). These once poisoned the
   censoring anchor — when it was `max(all dates)`, every open work's duration inflated to
   ~19 years. The anchor is now `max(recommendation_date)`.
5. **`ACTUAL_AMOUNT` is not expenditure.** 84,111 of 85,525 completed works have it exactly
   equal to `recommended_amount`; the 1,414 that differ span a ratio of **0.6798 → 1.00001**,
   with **zero** works above 1.05×. **Correction:** earlier project docs claim
   "85,524/85,525 identical" — that figure is wrong, though the conclusion (no usable
   expenditure variance, no cost-overrun signal) is unchanged and if anything stronger.
6. **Round-number bunching breaks a plain MAD.** In one 479-work peer group, 194 works sit
   at exactly ₹6.25L, collapsing MAD to ₹5,000 and giving a 79th-percentile work a robust-z
   of 10. Peer scale is now `max(MAD, IQR/1.349)` plus a 98th-percentile gate.
7. **Change-point detection was reading the calendar** — completion rate and delay are
   censoring-contaminated, so every recent quarter looked "changed". The change-point vector
   now uses only recommendation-time features.
8. **The temporal holdout leaked the future** — see §17.
9. **70 works are completed with no sanction record** — a genuine lifecycle inconsistency,
   surfaced as the conformance signal rather than silently repaired.
10. **No district column exists.** `implementing_agency` is a district administration
    office; `constituency_name` is a constituency. Any district-level claim would be invented.
11. **`CONSTITUENCY` is `"Sitting Rajya Sabha"`** for all RS works — a real value, not a
    placeholder, but not a place. This is why travel clusters key on state + constituency.

## 10. Cleaning rules

Every rule applied, in order, is in §5. In summary:

- **Dropped:** stage rows with a null join key (3,987); works with `recommended_amount <= 0` (6).
- **Flagged, never dropped:** back-dated (1,191), out-of-window dated (9),
  completed-without-sanction (70).
- **Nulled:** `delay_days` where dates are invalid (1,442 completed works affected).
- **Never done:** imputation, aggregation, outlier removal, renaming of raw files' internal
  columns, overrun computation.

## 12. Archetype discovery

`ACTIVITY_NAME` has ~180k distinct values and `WORK_CATEGORY` only 4 — neither can form a
peer group. So work types are **learned**:

| Property | Value |
|---|---|
| Embedding model | `sentence-transformers/all-MiniLM-L6-v2` (384-d, `max_seq_length=64`) |
| Descriptions embedded | 187,865 unique |
| Clustering | `MiniBatchKMeans`, `n_init=3`, `random_state=0` |
| K grid searched | 20, 30, 40, 50, 60, 80 |
| **K chosen** | **50** |
| Silhouette by K | 20: 0.041 · 30: 0.043 · 40: 0.044 · **50: 0.050** · 60: 0.049 · 80: 0.046 |
| Works assigned | 209,958 of 210,987 (**1,029 unassigned** — blank descriptions) |

Inspect via `features/archetype_features.csv` (`work_ref → archetype_id → archetype_label`)
and `models/archetype/archetype_catalog.csv` (`archetype_id → label, size, three example
descriptions`).

**Honest caveats you must not drop when presenting this:**

- **Silhouette is ~0.04–0.05 at every K.** K=50 wins by a hair. The clusters rest on
  **manual coherence review**, not that metric. Read the catalog examples and judge yourself.
- **Roughly 4 of 50 clusters are language/script artifacts** — Hindi/Gujarati transliterated
  descriptions grouped by script rather than work type (labels like `ke / pas / ghar`,
  `se / tak / ke`, `nirman / mandir / ke`, `kam / nu / game`). They still form valid peer
  groups; they are just semantically coarser.
- Labels are **auto-generated** from distinctive phrases (share × log-lift, share floor
  0.03, unigrams+bigrams). Descriptive only — not an official MPLADS taxonomy.

## 13. Completion-risk modelling

### Why survival analysis rather than regression or classification

This is the single most important modelling decision in the project.

**A regression on "days to complete" can only be fitted on works that completed.** 125,220
of 210,987 works (59%) have not completed. Dropping them is not a missing-data
inconvenience — it is **survivorship bias**, and it biases the answer in the direction that
matters most: the works most likely to be problematic are the ones that never finish, so
excluding them makes the portfolio look healthier than it is. The naive median delay over
completed works is **401 days**; that number describes the survivors, not the portfolio.

**A binary classifier ("will it complete?") is equally wrong**, because the label depends on
*when you look*. A work recommended last month and not yet complete is not a negative
example — it simply has not had time. Labelling it negative teaches the model that "recent"
means "failing", which is a calendar artifact, not behaviour. (This project made exactly
that class of mistake once, in change-point detection — see §14 — and it produced
convincing nonsense.)

**Survival analysis is the correct tool** because it models time-to-event with **censoring**:
an unfinished work contributes the information "did not complete within the *N* days we
observed it" without being forced into a completed/failed label. That is precisely the
information a regression discards and a classifier corrupts.

### Setup

| Aspect | Value |
|---|---|
| Event | reaching the `Works Completed` stage (`event_observed = True`) |
| Censoring | right-censoring at the extract as-of date (2026-05-26) |
| Events observed | 84,325 |
| Censored | 124,767 |
| Left truncation | entry at `STUDY_START = 2023-04-01` (eSAKSHI reporting start); works recommended earlier enter the risk set only at that date, via `entry_days` |
| Duration | `delay_days` if completed, else `as_of − recommendation_date` |
| Anomalous dates | back-dated / out-of-window rows have `delay_days` nulled and never enter the fit |
| Model | Cox proportional hazards (`lifelines.CoxPHFitter`, `penalizer=0.1`) |
| Covariates | `log_amount`, `is_sanctioned`, top-20 state dummies, top-40 archetype dummies (tail → `OTHER`) |
| Fit sample | 60,000 rows (`random_state=0`); the full set is not needed |
| Horizon | 365 days |
| Baseline curves | Kaplan-Meier per group available via `survival.km_baseline()` |

### Evaluation

| Metric | Value |
|---|---|
| **C-index (full-data fit)** | **0.6924** |
| **C-index (temporal-holdout training window)** | **0.7425** on n = 84,593 |

Calibration on the temporal holdout (`metadata/completion_risk_calibration.csv`):

| Predicted band | n | Mean predicted | Actual |
|---|---:|---:|---:|
| 0.0 – 0.2 | 75,501 | 0.088 | **0.101** |
| 0.2 – 0.4 | 8,531 | 0.258 | **0.275** |
| 0.4 – 0.6 | 561 | 0.406 | **0.267** |

Well calibrated where the mass is; **over-confident in the sparse top band** (561 works) —
a real limitation, not a rounding artifact.

### Outputs

`outputs/completion_risk_scores.csv` — 209,092 rows: `p_complete_horizon`, `hazard`,
`hazard_pct`, `rs_exposure`.

**`rs_exposure` = `recommended_amount × (1 − p_complete_horizon)`.** National total:
**₹5,219 crore** across open works. This is **exposure at risk — not loss, not missing
money, not fraud.** It is deliberately a simple product; the honesty is the point.

## 14. Behavioral/change-point modelling

Grain is **agency × quarter** (6,179 rows), not work. The actor is the implementing
authority; the question is *when* its behaviour shifted.

- **Vector used for detection** (all fixed at recommendation time): `n_works_in_period`,
  `log_median_amount`, `round_rate`, `templating_rate`.
- **Deliberately excluded**: `completion_rate`, `median_delay`, `backdated_rate`. These are
  censoring-contaminated — recent quarters have not had time to complete, so including them
  made *every* agency look like it "changed" at the recent edge. They remain in the file as
  reviewer context only.
- **Method**: binary segmentation maximising a max-t statistic on the standardized vector,
  corroborated by Jensen-Shannon divergence of the archetype mix across the split.
- **Partial final quarter is dropped** (the extract stops mid-quarter, so its volume is
  artificially low for everyone).
- Eligibility: ≥5 works per quarter and ≥6 quarters of history → **448 agencies** scored.

`outputs/entity_change_points.csv`. A change point is a **lead**: a new officer or a revised
guideline produces one too. The `change_description` column states this on every row.

## 15. Risk/triage

`outputs/triage_results.csv` — all 210,987 works, ranked.

`priority = 1 − Π(1 − wᵢ·sᵢ)` (noisy-OR) over seven signals:

| Signal | Weight | Family | Works fired |
|---|---:|---|---:|
| `conformance` | 0.75 | lifecycle | 1,270 |
| `peer_amount` | 0.60 | amount | 1,010 |
| `peer_delay` | 0.60 | duration | 255 |
| `completion_risk` | 0.60 | duration | 6,238 |
| `peer_stall` | 0.50 | duration | 254 |
| `change_point` | 0.50 | behaviour | 18,545 |
| `iforest` | 0.40 | multivariate | 2,110 |

**Confidence is the count of independent signal *families*, not signals.** `peer_stall` and

manufacture corroboration out of a single piece of evidence.

| Band | Works | Meaning |
|---|---:|---|
| NONE | 183,036 | no signal fired |
| LOW | 26,317 | 1 family |
| MEDIUM | 1,580 | 2 families |
| **HIGH** | **54** | 3+ independent families |

54 high-confidence leads out of 210,987 is a queue an auditor can actually read.

## 16. Audit-ROI optimization

`outputs/audit_plan.csv` and `outputs/audit_plan_baselines.csv`.

- **Capacity assumption: 100 auditor-days** — a demo assumption, not an official figure.
- **Cost model:** 1.0 day to open a travel cluster, 0.25 day for each further work in an
  already-open cluster. Travel clusters key on **state + constituency**, because all Rajya
  Sabha works share the constituency string `"Sitting Rajya Sabha"`; keying on constituency
  alone let an auditor hop between states for a quarter-day.
- **Objective:** `priority × money at stake × (1 + n_families)`, greedy on
  value-per-marginal-cost.

| Strategy | Works audited | Exposure covered |
|---|---:|---:|
| **audit-ROI plan** | **238** | **₹166.9 crore** |
| largest amount first | 100 | ₹135.2 crore |
| random selection | 100 | ₹2.2 crore |

238 works across **54 travel clusters**. The plan is a **recommendation for human approval**.
The system does not decide audits.

## 17. Temporal leakage rules

Read `temporal_availability` in the data dictionary before training anything.

| Class | Safe as a predictor? |
|---|---|
| `recommendation_time` | **Yes** — known when the work is recommended |
| `post_recommendation` | Only for post-sanction questions (`is_sanctioned`) |
| `post_completion` | **No — leaks.** `completion_date`, `delay_days`, `actual_amount`, `average_rating`, `work_id`, `is_backdated` |
| `as_of_extract` | Depends on pull date — `duration_days`, `event_observed`, `is_future_dated` |
| `model_output` | Never an input to the model that produced it |

**Two leaks were found and fixed in this codebase — do not reintroduce them:**

1. **Holdout leak.** `temporal_holdout()` originally fitted on durations observed through
   the end of the extract while claiming to stand at a 2024-07-01 cutoff. Result: predicted
   0.83 vs actual 0.13 in the top band. It now rebuilds the data as it looked on the cutoff
   date (works completed after the cutoff are re-censored at it).
2. **Censoring leak into behaviour.** Completion-derived features made every recent quarter
   look "changed" (§14).

## 18. Train/validation/test methodology

- **No fraud labels exist**, so there is no supervised train/test split for detection.
- **Completion-risk**: temporal holdout at `cutoff = 2024-07-01`. Fit on works recommended
  before the cutoff with the data reconstructed as-of that date; evaluate on what actually
  happened over the following 365 days. C-index + calibration table.
- **Anomaly ranking**: validated only on **synthetic injected anomalies**
  (`mplads_audit/validate.py`): AP 0.957, precision@100 1.00, recall@200 0.94, with every
  signal load-bearing under ablation (−0.20 to −0.25 AP). **Machinery metrics on planted
  anomalies — never a real-world fraud rate.**
- **Archetypes**: silhouette sweep + manual coherence review. Unsupervised; no split.

## 20. Known limitations

- No fraud labels → no supervised detection, no accuracy claim about fraud.
- Cluster quality rests on manual coherence, not silhouette (§12).
- ~4 of 50 archetypes are language artifacts (§12).
- Completion-risk is over-confident in its sparse top band (§13).
- Exposure is a deliberate product of risk × amount — exposure, not loss.
- The audit capacity (100 days) and cost model (1.0 / 0.25) are **assumptions**, not
  MoSPI-supplied figures.
- Change points have innocent explanations (new officer, revised guideline).
- Sanction **timing** is unknowable; only presence is testable.
- Some documents in `docs/` contain figures superseded by this package (§9.3, §9.5).

## 21. What data is NOT available

Not present in any public source, and therefore **never** modelled here:

- **Independent expenditure** — `ACTUAL_AMOUNT` is a completion confirmation (§9.5).
- **Payment tranches / amount released** — absent.
- **Estimated cost** — absent, so no estimate-vs-actual comparison.
- **Vendor / contractor identity** — `implementing_agency` is a government office.
- **GPS coordinates** — absent; no geospatial analysis.
- **Sanction date** — absent.
- **Progress percentage** — absent.
- **Asset photographs/documents** — `attach_id` proves they exist; the files are login-gated.
- **District** — no clean field.

## 22. What requires MoSPI/eSAKSHI access

A data grant would unlock, as drop-in additions to the existing engine: sanction dates
(lifecycle timing conformance), payment tranches and released amounts (payment anomalies),
estimated cost (true cost-overrun), vendor identity (collusion / repeat-winner analysis),
GPS (geospatial clustering), and attachment files (perceptual-hash photo reuse — currently
a **synthetic-only** module). `docs/DATA_REQUEST_EMAIL.md` requests exactly these gaps and
nothing already public.

## 23. Future data additions

Add new raw files to `data/raw/`, register provenance in `RAW_PROVENANCE`
(`mplads_audit/export_package.py`) and the filename in `config.RAW_STAGE_FILES`, document
every new column in `COLUMNS`, then re-run the exporter. The export refuses to write a file
containing an undocumented column, so the dictionary stays complete by construction.

## 24. Quick-start for an ML engineer

```python
import pandas as pd
```
